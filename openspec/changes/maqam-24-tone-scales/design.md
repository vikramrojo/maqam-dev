# Design

## Context

See proposal.md (Why) and the four specs for requirements. The current state that shapes the approach:

- **Pitch path.**
  - A note is a `uint8_t` MIDI number everywhere: `kb_map` → `kb_nt` / `pen_note` → `step_t.note[4]` → `trk_note_on(t, note, vel)` (`voice.c:364`).
  - The voice turns it into `pitch16 = note*16`, in 1/16-semitone units (`voice.c:273`), and indexes `PITCH_INC[2048]`, generated by `tools/gen_tables.py`.
  - Anything finer goes into a linear factor: `inc += (inc>>12) * (fine + tune_fine + q)` (`voice.c:607-609`, 1 cent ≈ 2.367 units of 1/4096).
- **Scales.**
  - `SCALE_MASK[]` is a list of 16 `uint16_t` 12-bit masks (`seq.c:22-40`), with the names in `N_SCALE[]` (`params.c:7`).
  - `kb_map` (`seq.c:100-147`) quantizes when a key is pressed (SNAP rounds down; WHITE walks degrees, with root = C4), so a step holds absolute notes.
  - `chord_notes` (`seq.c:149-181`) stacks degrees.
- **Step and project.**
  - `step_t` and `dstep_t` are both 10 bytes, enforced by an assert (`core.h:164`).
  - The project format is `FUN4`, with FNV checksum and importers for FUN1..3 (`project.c`).
  - `4*sizeof(project_t)` must fit the `.noinit` area (`tests/project_test.c:124`), which leaves about 550 B of headroom per project.
- **UI limits.**
  - Enum values on param pages are cut to 5 characters (`params.c:232`).
  - The editor's DESC reply sends at most 64 names in `ed_out[600]` (`editor.c:25,611`).
  - While a layer is held, EN_ALGO and EN_PRESET are drained unused (`ui_input.c:784-785`).
  - OCT− / OCT+ change the octave on press (`ui_input.c:828-837`).
- **Hardware.** JieLi AC79: 96 KiB RAM, code runs from flash (XIP). It is a unity build (`felucca.c`) with generated headers in `build/gen`.

## Goals / Non-Goals

**Goals:**
- One integer pitch model, a 24-tone grid plus cents, that 12-tone material passes through bit-identically.
- Scale data that new tunings can extend by adding data only (just intonation, more makams), with no new format change.
- Keep RAM and CPU flat. The only memory cost is 1 byte per step in projects.

**Non-Goals:**
- 53-tone or arbitrary-EDO note storage (the cent tuning tables cover Turkish).
- Zig-zag (vakra) phrase rules, seyir / pakad modeling, or jins-level modulation.
- Microtonal MIDI in/out (MPE, pitch bend, MTS).
- Per-note bends inside a chord step (the scale intonation is per note; the step bend is shared).

## Decisions

### D1. The quarter tone is bit 7 of the note byte
`p24 = (note & 127)*2 + (note >> 7)`. Helpers: `note_semi()`, `note_q()`, `note_from_p24()`.

- **Why:** zero bytes are added, the step keeps 4 notes, 12-tone bytes are unchanged, and the note byte stays the identity used for note-off and voice matching.
- **Alternatives:**
  - (a) Store `p24` (0..254) directly. Every note byte in projects, presets, the arp, MIDI and the drum maps would change meaning, so the risk is high.
  - (b) A separate per-note microtone byte, +4 B per step. That breaks the size budget.
- **Consequences:**
  - Every `& 127` / `< 128` on a note byte must be audited. A note byte is not a MIDI note.
  - The drum track and the SAMPLE GM-kit / SLICE paths never set the flag, since `kb_map` returns early for them.

### D2. Pitch arithmetic in the voice
`voice_start` and the MONO path compute `pitch16 = semi*16 + q*8 + whole16(cents)`. The rest of the cents, below 1/16 semitone, is stored in a new `int16_t bend_fine` (in 1/4096) and added to the existing `fine + tune_fine + q` sum.

- `cents` = the step bend + `tune[slot]`, clamped to ±100.
- Glide targets `pitch16`, so quarter tones glide correctly.
- The split mirrors the existing `G_TUNE` code at `voice.c:555-556`, so there is no dead zone.
- Engines that derive pitch from `m.pitch16` (sample `root16`, grain, formant) get it for free.
- **Alternative:** a 4096-entry `PITCH_INC` table at quarter-tone resolution. That doubles a flash table, and the semitone table already covers it exactly (8 units of 1/16).

### D3. A scale table generated as `scale_def_t`
```c
typedef struct { char code[6]; char name[9]; uint8_t set; uint32_t asc, desc; int8_t tune[24]; } scale_def_t;
```
- A new `tools/gen_scales.py` (standard library only) writes `build/gen/scales.h` from human-readable sources:
  - Turkish: comma steps.
  - Indian: swara strings plus just-intonation ratios.
  - Arabic: quarter-tone degrees.
  - Western: the existing 12-bit masks, spread to 24 bits.
- `tools/build.py` calls it next to `gen_tables.py`. The script also asserts: no two tune values in one slot, 5..12 degrees, degree 0 in both masks, unique codes of ≤5 characters, and the frozen order of indices.
- The expected output is listed in the appendix below, so a reviewer can check it without running the script.
- **Alternatives:**
  - Hand-written C arrays: masks and cents computed by hand can't be reviewed.
  - pytheory at build time: rejected. Its `MAQAM_RATIOS` are broken, its Arabic sets are inconsistent, it has no descending forms, and it pulls in scipy and sounddevice.

### D4. Intonation is applied at play time, not stored
`tune[(p24 - root) mod 24]` is looked up at note-on from the track's current scale and root.

- **Why:** it is per note (it works inside chords where the step bend is shared), it costs nothing in projects, and retuning a table changes old material consistently.
- **Trade-off:** changing the scale after recording retunes notes that happen to fall on degrees of the new scale. That is acceptable, and arguably desired: the scale is the tuning context.

### D5. Direction is chosen by key index, per track
`kb_last_key[track]` holds the last key pressed. If `k < kb_last_key`, use `desc`, otherwise `asc`; a repeated key uses `asc`.

- Comparing key indices, not output notes, avoids a circular dependency: which note plays depends on which mask is used.
- The result is baked into the note at key time, so playback, arp and MIDI never need direction state.
- **Alternative:** deciding at playback from the step order. That breaks with random arp orders and adds sequencer state.

### D6. SNAP rounds down from `2*semi + 1`
For even masks (WEST), `floor` into the mask from `2s+1` gives the same result as from `2s`. That is the compatibility guarantee, and `scale_test.c` EXPECTED proves it. For maqamat, both the ♭ key and the ♮ key reach the half-flat between them, which matches how players think of "the E of Rast".

### D7. OCT− / OCT+ as a modifier; octave change on release
- In `ui_input.c`, the octave change moves from press to release. A per-button "used" bit is set by any key press while the button is held.
- `kb_map` adds ∓1 quarter tone when OCT− / OCT+ is held on a synth track. In CHR this is chromatic; in SNAP the offset is applied before rounding, so a modifier can still reach a degree.
- On the step page, the same modifier makes NOTE move by quarter tones.
- **Alternatives:**
  - SCL as the modifier: it already opens the SCL layer.
  - A menu toggle: too slow for live play.
- **Cost:** about 50 ms of perceived latency on octave changes, because the change happens on release.

### D8. Scale sets in the UI; no saved set parameter
`SCALES[P_SCALE].set` is the source of truth.

- In the SCL layer, EN_PRESET (currently drained) cycles the set: it finds the first index with `set == next`.
- KNOB2 moves to the next or previous index with the same set, wrapping.
- **Why:** there are no new `P_*` / `G_*` values, so no parameter-count migration (`core.h:53-55`) and no web-mock param change beyond the list.

### D9. Root in quarter tones
`P_ROOT` max becomes 23, and `F_NOTE` formats from a 24-entry name table.

- The FUN4 importer doubles `P_ROOT`.
- The key-press root in the SCL layer sets `2*pc ± modifier`.
- Every reader of `P_ROOT` moves to the 24 grid: `kb_map`, `scale_keys`, the SCL screen and the SLICE base. The SLICE base uses `ROOT/2`, since slices are semitone-indexed.

### D10. Steps and the project format
- `step_t` gains `int8_t cents` (11 bytes). `dstep_t` gains `uint8_t rsv` to keep the same-size invariant, since the two are stored in a union or the same slots.
- The magic becomes `FUN5`. The FUN4 importer copies the steps field by field and is shaped like the existing FUN3 `step8_t` path.
- `proj_apply` drops `note &= 127` and clamps cents to ±63.
- Size check: +4 tracks × 64 steps = +256 B. That is about 3368 B against the ~3668 B `.noinit` limit and 3840 B `ST_PAYLOAD_MAX`. Both asserts stay.

### D11. Display glyphs
- Two glyphs are added to the `gfx.c` font: a reversed flat (half-flat) and a half-sharp (‡-like).
- `N_NOTE24[24]` uses them on screen. An ASCII form (`d` / `+`) is used by the web editor and in logs.
- A step tile with a non-zero bend appends `±Nc` when there is room. Otherwise a dot marks it.

### D12. Editor protocol
- STEP_GET / SET and TRACK_STEP append a `cents` byte (7-bit SysEx encoded with an offset of +64). Note bytes already travel as 7-bit values, so Q is sent as a separate 4-bit field: one bit per note.
- The protocol version goes up by one. The editor checks the version and hides cents for older firmware.
- DESC for SCALE sends the 52 codes: about 312 B of names, inside `ed_out[600]`.

### D13. Staying close to upstream SLOOP
This fork keeps merging upstream SLOOP releases while the firmware matures. The files this change touches (`seq.c`, `voice.c`, `ui_input.c`, `ui_layers.c`, `params.c`, `project.c`) are upstream's most active ones, so the implementation keeps its footprint in them small and easy to spot.

- **New logic goes in new files, called through short hooks.**
  - The 24-tone helpers, quantizing, direction tracking and intonation lookup go in a new `firmware/src/pitch24.h` (with `pitch24.c` if needed), included once from `felucca.c`.
  - Upstream functions (`kb_map`, `chord_notes`, `voice_start`, the step-page knobs) get a call into it, not a rewrite in place.
  - Where a function body has to change, the change is wrapped as a small block rather than reflowing the surrounding code.
- **Data lives in generated files.** All scale data comes from `tools/gen_scales.py` → `build/gen/scales.h`. Upstream files only see `SCALES[]` / `NSCALES` and a formatter. Adding or retuning a scale never touches an upstream file.
- **Each edit is labelled.** Every edit to an upstream file carries a short `/* maqam: ... */` comment, so `git grep "maqam:"` lists the fork's whole footprint for review during a merge.
- **No unrelated cleanup.** Upstream files get no renames, reformatting or opportunistic refactors, even nearby ones.
- **Merge before each task group.**
  - Pull upstream SLOOP before starting each `tasks.md` group, and run `tests/run_tests.sh` after the merge.
  - The golden hashes and `scale_test.c` WEST rows guard the 12-tone paths through merges.
  - When upstream changes the sound on purpose, take upstream's `golden.txt`, then re-check that the maqam paths still reduce to it (D2).
- **The project format is the riskiest merge.**
  - If upstream introduces its own next format (e.g. `FUN5`), this fork renames its own to the next free magic, and rebases its importer onto upstream's latest format, not FUN4.
  - Keep the fork's format code in one block of `project.c`: the magic, the step copy, and the ROOT ×2 / cents step, so it can be moved as a unit.
  - Recheck the size asserts after every upstream step or project change, because upstream may spend the same `.noinit` headroom.
- **The editor protocol and the web mirrors.**
  - The protocol bump (D12) follows the same rule: take upstream's version, then add one.
  - `web/editor.html` and its copy in `docs/webapp/editor/` are edited only in marked blocks, because upstream rewrites them often.

**Alternative: develop on a long-lived branch and merge once at the end.** Rejected, because the conflicts would compound across six hot files and the format code.

## Risks / Trade-offs

- **[Risk] A missed `& 127` somewhere silently drops quarter tones.** → Grep-driven audit task, plus a host test that runs the Q flag through key → record → step → play → arp → user preset.
- **[Risk] The size of the `FUN5` project breaks the `.noinit` assert.** → Compute it from `sizeof` in `project_test.c` before merging. Fallback: pack Q differently (no change) or reduce `rsv`.
- **[Risk] Users' muscle memory for OCT− / OCT+ (press vs release).** → Release is near-immediate. Document it in SLOOP.md. Drum-track behavior is unchanged.
- **[Risk] The musicology of the tables (descending forms, AEU commas, JI swaras) is wrong in places.** → The generator sources are readable lists. Ask a practitioner to review the 36 non-Western rows before release. Fixes are data-only.
- **[Trade-off] Intonation follows the current scale, not the recorded one.** → Documented; consistent with D4.
- **[Trade-off] MIDI out loses quarter tones.** → Explicitly out of scope. Notes still send correctly at their semitone.
- **[Risk] Upstream SLOOP merges conflict in the hot files or the project format.** → D13: new logic in `pitch24.h`, generated data, `maqam:`-labelled hooks, a merge before each task group, and format code kept in one block.
- **[Risk] Golden hashes drift because of arithmetic reordering in the voice pitch path.** → When q, cents and tune are all 0, the code path must reduce to the current expression. `regress.c` enforces this.

## Migration Plan

1. Firmware loads FUN1..FUN4 through the importers into FUN5 in RAM. Saving always writes FUN5.
2. Autosave and backups written by this firmware are FUN5. Going back to older firmware cannot read them. The release notes must tell users to export a backup before updating, as is already done for format changes.
3. The web editor detects the protocol version and degrades gracefully against older firmware (no cents column, 16 scales).

## Open Questions

- The exact pixel design of the two glyphs (to be settled while drawing them).
- Whether a non-zero bend shows as `±Nc` or as a dot on 16-tile step pages when space is tight (decided on the device).
